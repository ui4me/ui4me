# Local cross-platform development

Use this skill when a task needs this user's Linux development environment or the OmegaUI Windows development VM. First inspect the project's `AGENTS.md`, toolchain pins, documentation, Git state, and available commands. Project instructions and the current request take precedence. Paths and installed tools below are observations, not guarantees; verify them. Do not assume hosts are available to a cloud agent or that this skill grants access to unrelated machines or projects.

Run separate `xdotool` commands for typing and subsequent key presses. ## Linux native desktop

- Check `DISPLAY`, `WAYLAND_DISPLAY`, and the actual session before running GUI tests. Xvfb supplies X11; it does not by itself test Wayland. A nested KWin Wayland compositor on Xvfb worked on this machine. Select the Wayland backend explicitly when appropriate, use an isolated display/socket and runtime directory, and stop only processes started for the task.
- ui4me real-input harness: `tests/native/kwin/chat_journey.py` (plus `files_journey.py`, `dialog_journey.py`, `--plain` for self-checking probes) runs a private `dbus-run-session` + `kwin_wayland --virtual` and drives it with KWin fake_input. **Never let the private bus inherit the real `WAYLAND_DISPLAY`**: D-Bus-activated services (xdg-desktop-portal file chooser) would draw on the person's real desktop. The harness strips the display variables, sets the activation environment to the virtual socket, restarts portals that KWin's startup already activated, and reaps every process on the private bus at the end. Do not pipe the harness output into `grep` while it runs: leftover activated children can hold the pipe open.
- Capture real desktop observations when testing focus, input, resize, or compositor behavior. A renderer framebuffer snapshot, headless backend, or a running process alone does not prove those behaviors. Synchronize on events or observable state, use bounded timeouts, and avoid fixed sleeps as proof of correctness.

## Toolchains, packages, and tests

- Follow the project's pinned Rust toolchain and lockfiles; use locked Cargo resolution (for example `cargo test --locked`) and update locks only for an intended dependency change. For relevant Rust changes run the project's formatting and lint checks. Linux native builds may need a compiler, `pkg-config`, X11/Wayland and graphics development libraries; Windows needs appropriate MSVC build tools. Inspect missing prerequisites before installing them.
- Use an isolated Python virtual environment and the project's declared dependencies. Check supported Python versions and platform wheel tags. Build and install candidate wheels or source distributions in a clean environment outside the checkout; unset development native-library overrides and ensure imports resolve to the installed package. Test failure paths when they matter, not just import success.
- Use PowerShell 7 and the .NET SDK/version specified by the project, not Windows PowerShell 5.1 or whichever API happens to be newest. Check NuGet locked restore and the module manifest, then install the built module into an isolated directory and verify exports in a fresh process. Native GUI frameworks can bind an event loop to one process thread: test repeated applications in the same process and do not bypass thread checks. ScriptBlocks are runspace-bound; follow the binding's dispatch contract.
- Prefer the project's documented targeted build/test commands during iteration; run integration, packaging, and installed-consumer suites at the appropriate milestone. For ui4me, `docs/PROJECT_STATUS.md` and `python dev.py --help` describe `doctor`, `build`, `test`, `package`, `assemble`, and evidence commands; on this Linux host the system interpreter may be `python3`, not `python`.
- Native lifecycle or concurrency changes require meaningful owner-thread, cancellation, shutdown, callback, stale-handle, and repeated-session tests as relevant. Verify accepted work reaches a terminal outcome. Avoid nondeterministic timing and test both bindings when shared ABI behavior changes.
- Record exact source revision, OS, tool versions, test outcomes, and candidate artifact hashes. A test on one commit or package does not qualify another. Keep `passed`, `failed`, `blocked`, `interrupted`, and `not_run` distinct; missing tests are not successes. Keep credentials, generated binaries, screenshots, logs, and virtual environments out of Git.
- Builds and tests do not authorize publication. Only publish or alter remote release settings when the current user has explicitly requested it, and follow the project's release controls.
